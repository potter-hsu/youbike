## 一、表結構

### 1. `stations` — 站點慢變屬性

| 欄位 | 來源 | 說明 |
|---|---|---|
| `sno` | `sno` | 站點編號，PK |
| `name_zh` | `sna` | 站名（中文） |
| `name_en` | `snaen` | 站名（英文） |
| `area_zh` | `sarea` | 行政區（中文） |
| `area_en` | `sareaen` | 行政區（英文） |
| `address_zh` | `ar` | 地址（中文） |
| `address_en` | `aren` | 地址（英文） |
| `latitude` | `latitude` | 緯度 |
| `longitude` | `longitude` | 經度 |
| `quantity` | `Quantity` | 車柱總數。⚠️ **非可用容量**，見第三節 gap 說明 |
| `first_seen_at` | `DEFAULT now()` | 首次觀測到此站的時間，**upsert 時不更新** |
| `last_seen_at` | `now()` | 最近一次觀測到此站的時間 |

**SCD 策略：覆蓋更新（Type 1）**，不保留歷史版本。
理由：站名變更、站點遷移、車柱擴充皆為低頻事件，第 1 週不值得為此增加複雜度。
但 `first_seen_at` / `last_seen_at` 保留了「這站何時出現、何時消失」的粗粒度資訊，
未來若需升級為 Type 2（`valid_from` / `valid_to`），現有結構可平滑擴充。

> 站點數變化實測：8/4 為 1784 站，8/17 為 1789 站，8/25 為 1795 站。
> 新站由 upsert 自動納入，`first_seen_at` 記錄其首次出現時間。

### 2. `snapshots` — 時序觀測值

|---|---|---|
| `sno` | `sno` | 站點編號，PK 之一，FK → stations |
| `info_time` | `infoTime` | **該站回報數值的時刻**，PK 之一 |

### 3. `weather_stations` — 氣象測站慢變屬性

| 欄位 | 來源 | 說明 |
|---|---|---|
| `station_id` | `StationId` | 測站代碼，PK |
| `station_name` | `StationName` | 測站名稱 |
| `county_name` | `GeoInfo.CountyName` | 縣市 |
| `town_name` | `GeoInfo.TownName` | 鄉鎮市區 |
| `latitude` | `Coordinates[WGS84]` | 緯度。⚠️ **必須取 WGS84** |
| `longitude` | `Coordinates[WGS84]` | 經度 |
| `altitude` | `StationAltitude` | 海拔（公尺），決策 11 的篩選依據 |
| `first_seen_at` | `DEFAULT now()` | upsert 時不更新 |
| `last_seen_at` | `now()` | — |

**照收全臺灣測站（約 1342 站），不在寫入時篩選縣市。**
與「先照收，解讀留給查詢層」原則一致；臺北市 71 站的篩選發生在對應表建立時。

> ⚠️ `Coordinates` 是陣列，同時含 TWD67 與 WGS84 兩組座標，**順序不保證**。

> 取錯會使所有距離計算系統性偏移。必須以 `CoordinateName` 篩選，不可取 `[0]`。

| `precipitation_10min` | O-A0002 `Past10Min` | 過去 10 分鐘累積雨量（mm） |
| `precip_10min_flag` | 同上 | 特殊碼原值，正常時為 NULL |
| `precipitation_1hr` | O-A0002 `Past1hr` | 過去 1 小時累積雨量 |
| `precip_1hr_flag` | 同上 | — |
| `weather` | O-A0003 | 天氣現象（「陰有雨」等 60 種組合） |
| `visibility` | O-A0003 | 能見度描述（`>30`、`<1`、`11-15`），非數值 |
| `sunshine_duration` | O-A0003 | 日照時數 |
| `wind_direction` | O-A0003 | 風向（度） |
| `wind_speed` | O-A0003 | 平均風速（m/s） |
| `air_temperature` | O-A0003 | 氣溫（°C） |
| `relative_humidity` | O-A0003 | 相對濕度（%） |
| `uv_index` | O-A0003 | 紫外線指數 |
| `first_fetched_at` | **檔名解析** | upsert 時不更新 |
| `last_fetched_at` | **檔名解析** | — |
| `loaded_at` | `DEFAULT now()` | — |

**主鍵：`(station_id, obs_time)`**，與 `snapshots` 同樣的自然鍵設計。

**兩個資料集寫入同一張表，分兩次 upsert：**
1. O-A0002（71 站，僅雨量）
2. O-A0003（9 站，溫濕風）——為前者的子集，會撞主鍵

> ⚠️ 第二次 upsert 的 `ON CONFLICT DO UPDATE` **只能更新氣象要素**。
> 若 SET 中包含 `precipitation_*`，`EXCLUDED` 值為 NULL（該 INSERT 未提供），
> 會把第一次寫入的雨量蓋掉。
> 同「snapshots 撞到只更新 `last_fetched_at`」的思考，但要保護的欄位更多。

**降雨為何只存 10min 與 1hr，不存 3hr 以上：**
`Past1hr` 代表累積效應（連下一小時 vs 剛開始飄雨，兩者 `Past10Min` 可能相同
但行為影響不同）。3hr 以上超出騎乘決策的反應尺度，且有時序資料可自行聚合。

### 7. `fetch_log` / `load_log` — 系統行為紀錄

記錄的不是觀測資料，而是**程序做了什麼**。

**`fetch_log`**

| 欄位 | 說明 |
|---|---|
| `fetch_id` | `bigserial` PK |
| `started_at` | 抓取開始時間 |
| `duration_ms` | 耗時 |
| `status_code` | HTTP 狀態碼 |
| `etag` | 回應的 ETag |
| `content_length` | header 宣告的長度，可與實際寫入 bytes 比對 |
| `update_time` | 整包資料的 `updateTime`（全站共用，不進 snapshots） |
| `stations_received` | 收到幾個站 |
| `saved_file` | 本次存下的檔名，供 log 與檔案對應 |
| `error_message` | 失敗原因，成功則為 NULL |

**`load_log`**

| 欄位 | 說明 |
|---|---|
| `load_id` | `bigserial` PK |
| `fetch_id` | FK → fetch_log，關聯同一次執行的兩階段 |
| `started_at` | — |
| `duration_ms` | — |
| `files_processed` | 本批處理幾個檔案 |
| `files_skipped` | 跳過幾個（解析失敗） |
| `rows_affected` | 影響列數 |
| `error_message` | — |

> ⚠️ **尚未實作寫入。** 表已建立（8/18），程式未動。

**為何拆成兩張表（2026-08-18 重新設計）：**

原始設計假設 fetch 與 load 是分開的程序。但 8/16 起 `fetch.py` 抓完直接呼叫 load，
**一次 cron 執行包含兩個階段**。

8/18 的故障即為「fetch 全部成功、load 全部失敗」——
若只記 fetch，這張表會顯示 288 筆漂亮的成功記錄，完全看不出資料庫停在 8 小時前。

兩者關心的東西也不同：fetch 是 HTTP 層（status code、ETag），
load 是資料庫層（處理幾檔、跳過幾檔）。硬塞同一張表會有一半欄位永遠是 NULL。

**粒度：一次執行寫一列，非每檔一列。** 每檔一列會產生 28800 列/天，
而需要知道的只是「這批有沒有跳過檔案」；是哪個檔案壞掉放進 `error_message` 即可。

**移除 `rows_inserted` / `rows_updated`，合併為 `rows_affected`：**
原設計分兩欄是未實作前的猜測。實際上 `cur.rowcount` 在 upsert 情況下分不出插入與更新，
要區分需改 SQL（`RETURNING xmax = 0`），而「插入 1500 / 更新 284」比
「影響 1784」多提供的資訊很少。需要時再加。

**⚠️ 設計驗證（以 8/18 的故障為測試案例）：**

問題：「若當時有這兩張表，查得出 13:55 之後 load 全掛嗎？」

第一直覺是查 `files_skipped` ——**那是錯的**。當時 load 每次都直接 crash，
根本沒機會寫 `load_log`。正確的訊號是**記錄本身消失**：

```sql
-- 過去 24 小時每小時有幾次 load？（正常 12 筆）
SELECT date_trunc('hour', started_at), count(*)
FROM load_log GROUP BY 1 ORDER BY 1;
```

**監控要看兩種訊號：內容異常（`files_skipped > 0`）與記錄消失（某小時零筆）。**
後者通常更嚴重——它代表程式死了，不是資料有問題。

這也解釋了決策 7 為何讓欄位允許 NULL：失敗的執行也要留下一列，
否則只能靠「沒有記錄」推斷，訊號較弱。

判準：第 6 週要能只靠這兩張表回答「系統過去 24 小時正常嗎」。

## 二、關鍵決策與理由

### 決策 1：切多張表，而非單一寬表

站點靜態屬性（站名、地址、經緯度）若隨每次快照重複儲存，
以 1784 站 × 288 次/天計算，一天將重複寫入約 51 萬次相同文字。

`fetch_log` / `load_log` 獨立的理由不同——它們記錄的是**系統狀態**而非**觀測資料**，
兩者的生命週期、查詢模式、保留策略都不同。

**沒有它們就無法區分「抓了但資料沒變」與「程序掛掉沒抓」**，
第 6 週的監控會失效。

---

### 決策 2：主鍵用 `(sno, info_time)`，不用 `(sno, fetched_at)`

**背景：** 觀測到有站點失聯超過一年半（捷運東門站 3 號出口，`infoTime` = 2025-02-27），
API 仍每次照常回傳，外觀與正常站無異。

| 主鍵選擇 | 該站 288 次抓取後的列數 |
|---|---|
| `(sno, info_time)` | **1 列** |
| `(sno, fetched_at)` | 288 列 |

選前者的理由：

1. **天然冪等**——同一份資料重複抓取，寫入結果不變，直接滿足第 2 週需求
2. **不產生假紀錄**——失聯站不會生成 288 筆/天標著今日時間卻是舊值的資料，
   避免污染第 4 週的因果估計（該序列會是一條完全靜止的假時間序列）

代價是丟失「我在某時刻確實抓到這站」的資訊，
以 `last_fetched_at` 欄位補回：撞主鍵時更新此欄。

**附加價值：** `last_fetched_at - info_time` 即為該站的資料延遲，
不需另外計算，資料新鮮度監控可直接查詢。
（此式成立的前提見決策 10。）

實作對應 PostgreSQL 的 `INSERT ... ON CONFLICT DO UPDATE`（upsert）。

**upsert 語句：**
```sql
ON CONFLICT (sno, info_time) DO UPDATE SET
    last_fetched_at = EXCLUDED.last_fetched_at,
    loaded_at       = now()
```

> ⚠️ 兩個實作要點：
> 1. `first_fetched_at` **不出現在 SET 裡**——一旦更新即永久失去「首次觀測」資訊
> 2. `last_fetched_at` 用 `EXCLUDED.last_fetched_at`（新檔案的抓取時間），
>    **不是 `now()`**。理由見決策 10

**8/14 實測驗證：** 東門站在 `snapshots` 中僅 1 列，
`last_fetched_at - info_time` = 532 天 14 小時，符合設計預期。

**副作用（8/28 發現）：** 此設計使「無借還活動時不產生新列」，
故深夜觀測數僅為白天的 1/10（原始資料亦然，非查詢條件造成）。
分析樣本因此天然條件在「有活動的時刻」上，見第五節。

---

### 決策 3：`Quantity` 歸 `stations`

**驗證方法（2026-08-06）：** 取 8/4、8/5 兩個時間點的快照，
篩選 `act = '1'` 且 `gap ∈ [1,5]` 的站，以 `sno` merge 後比對。

**結果：** 317 站中，`Quantity` 變動筆數為 **0**。單日內無變動，屬慢變欄位。

**2026-08-25 長期複驗嘗試：**

原訂「累積 2 週資料後回頭複驗」。實際嘗試時發現**此複驗在資料庫層做不到**——
`quantity` 位於 `stations` 表且採 Type 1 覆蓋更新，每個 `sno` 僅一列，
歷史值已被抹除。任何 `count(DISTINCT quantity)` 查詢必然回傳 1。
若要驗證需回頭比對 raw 檔案。

**決定暫不執行。** 理由：
- 實際影響有限。已知 `quantity` 不可作為容量分母（見第三節 gap 說明），
  建模使用的是 `rent + return`，該值每筆快照皆有
- 若驗出有變動，需改 schema 並回填歷史，成本不小
- 第 4 週建模優先

**附帶發現：** Type 1 SCD 的代價在此具體浮現——
8/6 選擇覆蓋更新時，未預見它會使日後的複驗失去依據。

---

### 決策 4：`act` 存進 `snapshots`，每筆重複

`act` 本身是慢變欄位（一年可能僅變動數次），照理應歸 `stations`。
但觀測到一個現象改變了判斷：

**`act = 0` 的站點，其 `infoTime` 呈現群聚：**

```
2026-07-10 06:57:04  溫州停車場、古亭站、動物園站、濟南紹興、螢橋公園
2026-07-10 06:58:02  潭美街、東湖國小、東湖一號公園、西湖國中、八仙里、薇閣
2026-07-10 06:59:02  復華花園、龍山寺、洛陽停車場
2026-07-10 07:28:04  榮星花園、林安泰、中山北路、南京新生
```

秒數完全相同、橫跨不同行政區、間隔約一分鐘
→ 這是**一次批次操作**，而非各站獨立故障。

**推論：** `act` 反映營運決策（施工、汰換、季節性停用），
若觀測期間內有站被停用，對該站的時間序列而言是**結構性斷點**，
不可當作雜訊濾除。

若 `act` 僅存最新值於 `stations`，將永遠無法得知某站何時被停用。
存入 `snapshots` 後，可用 window function（`LAG`）直接查出狀態轉換時點。

單一字元的重複儲存成本，遠低於遺失狀態變更歷史的代價。

**`act = 0` 有兩種型態：**
- A 完全離線：`rent = 0, return = 0`，gap = Quantity
- B 空站可還：`rent = 0, return = Quantity`，**等式成立**

→ 僅用「等式不成立」篩選異常站會漏掉型態 B。

**建模應用：** 分析樣本要求 `act = '1' AND prev_act = '1'`，
排除跨越結構性斷點的差值。

---

### 決策 5：建兩個索引

| 索引 | 服務的查詢 |
|---|---|
| `(sno, info_time)`（主鍵自帶） | A：單站的時間序列（建模用） |
| `(info_time)` | B：某時刻的全市橫斷面（空間分析用） |

複合索引 `(sno, info_time)` 以 `sno` 為第一排序鍵，
查詢 B 僅提供 `info_time` 條件時無法利用，故需獨立索引。

每個索引都會增加寫入成本與儲存空間，兩個是合理起點，不預先過度建置。

---

### 決策 6：不儲存的欄位

| 欄位 | 原因 |
|---|---|
| `mday` | 與 `infoTime` 完全相同 |
| `srcUpdateTime` | 與 `updateTime` 完全相同 |
| `infoDate` | 可由 `info_time` 導出 |
| `updateTime` | **全站 1784 筆共用同值**，屬「整包資料」的屬性而非站點屬性 → 移至 `fetch_log` |

---

### 決策 7：型別與約束

**`sno` 用 `text` 而非 `integer`**
原始資料為字串（`'500101001'`）。編號類欄位不做算術運算，
且轉整數有吃掉前導零的風險。

**`act` 用 `text` 而非 `boolean`**
原始為 `'0'` / `'1'` 字串。轉 boolean 屬於「解讀」——
若未來出現第三種值將無處安放。
與 raw layer 原則一致：**先照收，解讀留給查詢層**。

**`NOT NULL` 的取捨**

| 範圍 | 決定 | 理由 |
|---|---|---|
| `name_zh`、`area_zh`、經緯度 | NOT NULL | 缺值即無法使用，寧可寫入時就失敗 |
| 英文欄位 | 允許 NULL | 屬附加資訊，部分站點可能缺漏 |
| `weather_stations.altitude` | NOT NULL | 決策 11 的篩選依據，缺值即無法配對 |
| `fetch_log` / `load_log` 幾乎全部 | 允許 NULL | **失敗的執行也必須記錄** |

最後一項是關鍵：連線 timeout 時 `status_code`、`etag`、`stations_received` 皆取不到。
若設 NOT NULL，**最需要留下紀錄的那一次反而寫不進去**。

**`fetch_id` 用 `bigserial` 而非 `serial`**
`serial` 上限約 21 億。以當前寫入量（288 筆/天）遠不會觸及，
但型別變更的成本現在為零、資料累積後為遷移作業。

**主鍵型態：natural key vs surrogate key**
`snapshots`、`weather_obs` 使用複合自然鍵——資料本身已具唯一識別。
`fetch_log` / `load_log` 無天然唯一組合（用 `started_at` 需假設不會有並行執行，
排程重疊或手動測試時即失效），故使用流水號。

---

### 決策 8：觀測表對測站表設外鍵

`snapshots.sno` → `stations.sno`，`weather_obs.station_id` → `weather_stations.station_id`。

保證觀測表不會出現未知站點的資料。

**代價：寫入有順序依賴**——新站必須先寫入維度表才能寫觀測表，
否則違反外鍵約束。`load.py` / `load_weather.py` 中 `executemany` 的順序不可對調。

---

### 決策 9：資料延遲不在寫入時過濾

**決定：** 全部寫入，資料新鮮度的判斷交給查詢層。

**理由一（主要）：避免 selection bias**
站點失聯不是隨機事件——極端天氣可能導致特定區域的站集體斷線。
若在寫入時過濾，樣本將變成「天氣事件中仍存活的站」，
這是被自變數篩選過的樣本，會使第 4 週的因果估計產生偏誤。

「哪些站在何時失聯」本身即為資料，不是雜訊。

**理由二：門檻可調**
寫入時過濾則門檻固定，過濾掉的資料無法還原。
留在表中則隨時可依分析需求調整。

**成本評估：** 因主鍵為 `(sno, info_time)`，失聯站不論抓取幾次僅佔 1 列，
儲存成本趨近於零。

**與既有決策的一致性：** 同「raw 存 `response.text`」「`act` 不轉 boolean」，
皆為「先照收，解讀留給查詢層」原則的應用。

**查詢層實作：** 分析樣本採 `last_fetched_at - info_time < interval '15 min'`。

### 決策 10：`fetched_at` 與 `loaded_at` 分離

**問題發現：** 8/13 用 8/10 的檔案測試 load，
查詢 `last_fetched_at - info_time` 得到「1784 站全部 stale」。
實際原因是 `last_fetched_at` 填的是 `now()`（入庫時刻），
混入了三天的處理延遲。

**兩種延遲的性質不同：**

| 算式 | 意義 | 影響 |
|---|---|---|
| `last_fetched_at - info_time` | 資料延遲：該站多久沒回報 | 分析正確性（篩除失效觀測） |
| `loaded_at - last_fetched_at` | 處理延遲：檔案躺多久才入庫 | 系統健康監控 |

**決定：**
- `first_fetched_at` / `last_fetched_at` 由**檔名解析**（`%Y%m%dT%H%M%z`），非 `now()`
- 新增 `loaded_at`，用 `DEFAULT now()`
- 前兩者移除 `DEFAULT`——值應由程式提供，留著 DEFAULT 會在漏傳時安靜填入錯誤值

**為何不採用「讓 load 緊跟 fetch，時間差可忽略」：**
該方案將兩種延遲壓成一個數字，靠假設維持正確性。
若 load 中斷數小時後補跑，該區間的 `data_lag` 會虛增，
且**無法從資料中看出**——第 4 週若以 lag 門檻篩選樣本，會誤刪一批完好的觀測。

**與既有原則一致：** 同「先照收，解讀留給查詢層」，不在寫入時壓縮資訊。

**8/14 實測驗證：**
```
 data_lag |      process_lag
----------+------------------------
 00:01:58 | 4 days 21:52:06.849042
 00:08:42 | 4 days 21:52:06.849042
 00:14:55 | 4 days 21:52:06.849042
```
`data_lag` 各站不同（1~15 分鐘，真實回報延遲）；
`process_lag` 全部相同（該批檔案的入庫延遲）。兩者成功分離。

> 實作細節：`now()` 回傳**交易開始時間**，同一 transaction 內多次呼叫值相同
> （上表微秒完全一致即為此故）。
> 這正是所需行為——一次 load 即一個處理事件，該批所有列應共用時間戳。
> （若需逐次求值為 `clock_timestamp()`。）

### 決策 11：空間對齊——最近測站，但先排除高海拔

**背景：** 臺北市有 71 個雨量站（O-A0002）、9 個綜觀站（O-A0003），
後者為前者的子集。

**觀測（2026-08-19 15:00 實測）：**

| 測站 | 海拔 | 當日累積雨量 | 氣溫 |
|---|---|---|---|
| 鞍部 | 838m | 14.0 mm | 23.0°C |
| 陽明山 | 607m | 12.5 mm | 24.4°C |
| 臺北（中正） | 6m | **1.0 mm** | 29.4°C |

**同一時刻、同一城市，山區與市區雨量差 14 倍、溫度差 6 度。**
→ 全市共用單一天氣值不可行。

**但純水平距離也有問題：** 71 站中約 16 站海拔 > 300m
（大屯山 1079m、小油坑 814m、擎天崗 769m 等），集中於北投、士林、文山。
YouBike 站點幾乎全在平地市區，若以水平距離配對，
部分站會被配到海拔相差數百公尺的測站。

**決定：先篩選海拔 < 150m 的測站，再做最近距離配對。**

門檻理由：
- 150m 以下仍有約 50 站，密度足夠（臺北市 272 km²，約每 5 km² 一站）
- 該門檻切在「市區丘陵」與「陽明山系」之間
  （保留關渡 111m、雙溪 127m、劍南路 121m；排除貴子坑 278m、貓空 317m）

**未採用：氣象署格點資料**（O-A0038-003、O-A0040-004）
覆蓋完整且無測站失聯問題，但時間粒度為小時／日，過粗。
且格點值為模式分析輸出而非實測，其誤差可能具系統性，
對因果估計的影響比實測站的隨機測量誤差更難處理。

**未採用：PostGIS**
只做一次的一對多最近配對，不值得增加相依。
Haversine 以純 SQL 實作即可（`sin`/`cos`/`asin`/`radians` 皆為內建函式）。
若日後需範圍搜尋或 K 近鄰查詢，空間索引才有價值。

**實作結果（2026-08-25）：**
- `sql/station_weather_map.sql`，1795 站全數配對
- 距離 min 17.3m / avg 873m / max 2139m —— 無測站盲區
- 最大負載測站 C0AH70 服務 134 站
- ⚠️ 同測站下的站點共用天氣值 → 標準誤需以 `station_id` cluster。
  處理變數的有效變異來自 50 個測站，而非 1795 個站點

### 決策 12：時間對齊——取觀測時刻之前最近的一筆天氣

**背景：** YouBike 每 5 分鐘一筆，天氣每 10 分鐘一筆。

**問題：** YouBike 於 15:05 的觀測，應配對 15:00 或 15:10 的天氣？

**決定：往前取（15:00 那筆）。**

**理由：** 15:05 的可借車輛數反映 15:00–15:05 間的借還行為。
而 `Past10Min` 為過去 10 分鐘累積，故 15:10 那筆涵蓋 15:00–15:10，
**包含了 15:05 之後才發生的降雨**——以未來資訊解釋當下行為，
構成 look-ahead bias。

**已知代價：** 15:00 那筆涵蓋 14:50–15:00，與被解釋的時段落後 5–15 分鐘，
存在測量誤差。但降雨具時間持續性（前 10 分鐘有雨時當下多半仍在下），
且測量誤差造成的衰減偏誤（attenuation bias）方向明確、
較內生性易於處理與說明。

**取捨原則：寧可承受測量誤差，不引入內生性。**

**實作：** 將 `info_time` 往下取整到 10 分鐘，直接對上 `obs_time`：
```sql
date_trunc('hour', info_time)
  + interval '10 min' * floor(extract(minute from info_time) / 10)
```
氣象署的 `obs_time` 皆為整 10 分鐘，取整後即精確配對，無需 LATERAL JOIN。
已驗證每筆 `info_time` 對應唯一一筆天氣觀測。

**附帶佐證：** 氣象署有 7–10 分鐘的發布延遲（15:27 抓取取得 15:20 的觀測），
實務上也只拿得到過去的資料。

### 決策 13：降雨與溫度使用不同的空間對應

**問題發現（2026-08-26）：** 分析樣本中 `air_temperature` 缺失率達 **100%**。

**原因：** 71 個雨量站中僅 9 站具完整氣象儀器。
以「所有低海拔測站」為候選做最近配對時，多數 YouBike 站會被配到只有雨量筒的測站，
永遠取不到溫度。

**決定：建立第二張對應表 `station_temp_map`，候選集合限制在有溫度觀測的測站。**

**根據：兩種氣象要素的空間尺度不同**

| 要素 | 空間變異 | 所需測站密度 |
|---|---|---|
| 降雨 | 大——對流性降雨可隔一公里就沒了 | 高（71 站） |
| 溫度 | 小——都會平地間差異小，主要受海拔影響 | 低（6 站足夠） |

**2026-08-26 執行時符合條件的 6 站：**
```
466920 臺北 6.3m    C2AA10 中八仙 16m   A0A010 臺灣大學 17m
CAAH60 大安森林 18m  CAA090 國三甲005K 60m  CAA040 國三S016K 71m
```
分布涵蓋中正、北投、大安、文山、南港，東西南北皆有覆蓋，海拔 6–71m 相近。

**實作結果：**
- 1795 站全數配對，溫度缺失率由 100% 降至約 7%
- 距離 min 79.4m / **avg 2869m** / max 7248.9m，172 站（9.6%）超過 5km

> ⚠️ 溫度的配對精度比降雨差三倍以上（2869m vs 873m）。
> 都會平地的溫度梯度小（7km 外通常差 1–2°C），可接受，
> 但穩健性檢查應另跑「僅保留 `temp_dist_m < 3000`」的樣本。

> ⚠️ 候選集合來自動態子查詢（`WHERE air_temperature IS NOT NULL`）。
> 若日後有測站開始／停止回報溫度，重跑結果可能不同。上列 6 站為當時的基準。

## 三、已知資料特性（影響後續建模）

### ⚠️ 欄位名稱與官方文件不符

計畫文件參考的是舊版 API，實際回傳完全不同：

| 舊版文件 | 實際欄位 |
|---|---|
| `tot` | `Quantity` |
| `sbi` | `available_rent_bikes` |
| `bemp` | `available_return_bikes` |
| `lat` / `lng` | `latitude` / `longitude` |

氣象署亦同：`fields` 宣告的是扁平欄位名，實際回傳為巢狀結構
（`Station[].WeatherElement.Now.Precipitation`）。

**一律以實際回傳為準。**

---

### `gap` 是動態的，不可用 `Quantity` 當可用容量

定義 `gap = Quantity - available_rent_bikes - available_return_bikes`。

**觀測：**
- 全體站點中 `gap > 0` 者佔 35.6%（635/1784）
- 無負值（`rent + return ≤ Quantity` 恆成立）
- `gap` 分布呈幾何遞減：0→1147, 1→402, 2→136, 3→38, 4→12, 5→12
- 另有約 30 筆 `gap ≈ Quantity`，數量與 `act = 0` 的 29 站吻合 → 即離線站
- 跨日比對（317 站）：差值分布對稱，0→186, ±1→96, ±2→23, ±3→9, ±4→3

**解讀：** 差值有增有減，代表佔用車柱的物件會流動，
而非「柱子陸續損壞」的單向累積。
最可能的解釋是充電中的電輔車——電量不足時不可借、佔用車柱，充飽後回到可借狀態。
（此為推論，可透過檢驗 `gap` 是否具日內週期性驗證，非當前優先事項。）

**對建模的影響：**
> 使用率不可計算為 `available_rent_bikes / Quantity`，
> 分母會系統性偏大。實際可用容量為 `rent + return`。

---

### ⚠️ 氣象資料的特殊代碼

| 代碼 | 意義 |
|---|---|
| `X` | 儀器故障 |
| `T` | 雨跡——有降水但低於儀器刻度（翻斗式雨量計約 0.5mm） |
| `-99` | 缺值或資料異常 |
| **`-98`** | **連續 6 小時無降水 → 語意即 0** |
| `990` | 風向不定（僅風向欄位） |

**`-98` 最關鍵**：若把所有負值當缺值丟棄，會系統性地丟失「沒下雨」的時段
→ 樣本被自變數篩選過 → selection bias（同決策 9 的問題）。

**轉換規則：**

| 原始值 | 數值欄位 | flag |
|---|---|---|
| `"15.5"` | 15.5 | NULL |
| `"-98"` | **0.0** | `'-98'` |
| `"T"` | **0.0** | `'T'` |
| `"-99"` / `"X"` | NULL | 該碼 |
| 未知代碼 | NULL | 原字串 |

**降雨做 flag、溫濕風不做**，判準是「不同的碼是否需要不同處理」：
- 降雨有三種處理方式（0／0／NULL）→ 需要 flag
- 溫濕風的 `X` 與 `-99` 在建模時處理方式相同 → 直接 NULL

**未知代碼存入 flag 而非拋出例外**——8/18 的教訓：
不讓意外輸入炸掉整支程式，而是留下可查詢的痕跡。

**`T` 暫存 0**，第 4 週應做敏感性分析（改為 0.05 看估計是否穩健）。

---

### 氣象資料的其他特性

**發布延遲 7–10 分鐘。** 15:27 抓取取得 15:20 的觀測。
對離線分析無影響；若第 5 週做即時儀表板，天氣欄位會永遠落後一個週期。

**O-A0003 溫度缺失約 6–17%（降雨完整）。**
推測為該時刻回傳的 `Station` 陣列未包含某些測站。
影響小——溫度慢變（10 分鐘變化 < 0.3°C），插補誤差可忽略。
⚠️ 但**單一時刻取樣會誤導**：曾出現某批樣本溫度 100% 缺失，
實為該時刻恰好落在發布空窗，整體缺失率僅 7%。

**抓取失敗約 5%。** 氣象署偶發 `TimeoutError`，retry 三次仍失敗即放棄該輪。
不像 YouBike 有 raw 檔案可補——沒抓到就是永久遺失。
> retry 間隔僅 1s + 2s，而 cron 週期 10 分鐘，可考慮拉長退避。

**0.5mm 堆積嚴重。** 非零降雨觀測中 75% 為 0.5mm（雨量計最小刻度）。
翻斗式雨量計需累積 0.5mm 才翻斗，故「這 10 分鐘 0.5mm」
可能是前幾個時段的雨水在此刻翻斗 → 測量誤差偏向延遲。

---

### 時間欄位：`TIMESTAMPTZ` + Python 端標記時區

原始資料的時間欄位皆為 `YYYY-MM-DD HH:MM:SS`，**不含時區標記**。
經與抓取時間比對，判定為 UTC+8。

**決定：欄位型別用 `TIMESTAMPTZ`，時區資訊在 Python 端補上後才寫入。**

**理由：** 若寫入不帶時區的字串到 `TIMESTAMPTZ`，PostgreSQL 會依「當下連線的
timezone 設定」補值。本機為 Asia/Taipei、EC2 預設為 UTC，同一份資料會差 8 小時，
且**不會報錯**——第 4 週跑模型時才會發現尖峰落在半夜。
更糟的是本機寫入的舊資料正確、雲端寫入的新資料錯誤，兩批混在同一張表。

在 Python 端明確標記後，資料庫收到的已是帶時區的值，
正確性不依賴部署環境的設定。

**實作：**
- `info_time`：`strptime(..., "%Y-%m-%d %H:%M:%S")` → `.replace(tzinfo=ZoneInfo("Asia/Taipei"))`
- `fetched_at`：`strptime(..., "%Y%m%dT%H%M%z")` —— `%z` 直接解析檔名中的 `+0800`
- 氣象署 `obs_time`：`datetime.fromisoformat(...)` —— 已自帶 `+08:00`，無需處理

**替代方案（未採用）：** 用 `TIMESTAMP` 並全系統約定台北時間。
較簡單，但該約定只存在文件中、無機制強制，
且第 3 週接入氣象署資料後將有多種時間格式並存，靠約定難以維持。

**8/17 實地驗證：** EC2 系統時間為 UTC，程式仍正確產出 `+0800` 檔名，
資料庫中的 `info_time` 與本機一致。決策成立。

### `sarea` 並非全為行政區

除「大安區」「中正區」等行政區外，另有「臺大公館校區」等非行政區值。
若進行行政區層級的彙總分析，此類值將成為孤兒類別。

**目前處理：** 原樣儲存，不做正規化。
若需行政區分析，再建立對應表處理。

## 五、建模相關發現（2026-08-28）

> 本節記錄使用此 schema 進行因果分析時浮現的問題。
> 內容若持續增長，應拆為獨立文件。

### 應變數：`delta` 而非 `delta / gap_min`

原本將觀測間隔塞進分母做標準化。**該做法強制假設「變化量與間隔成正比」，實測不成立**：
`gap_min` 作為控制變數時係數僅 0.0043/分鐘，遠小於平均變化率。

後果：對應變數 trimming 時係數從 0.0121 掉到 0.0045。
診斷發現被砍掉的觀測 `gap_min` 中位數為 2–3 分鐘（全樣本 6.3 分鐘）
→ trimming 砍的是**短間隔觀測**（分母小、數值被機械性放大），而非變化大的觀測。

**修正：用原始 `delta`，`gap_min` 改為控制變數。**

### 穩健性檢查應對處理變數 trimming，不對應變數

若處理會使應變數變大，砍掉大的應變數等於優先砍掉受處理影響最強的觀測
→ 係數必然縮小，即使不存在極端值污染。

診斷方式：檢查被砍掉的觀測中處理組比例是否與全樣本相近。
實測顯示比例未隨門檻收緊而單調上升，故非此問題。

### 面板索引必須用 `obs_slot`，不可用 `info_time`

`info_time` 是各站自行回報的時刻，四天有數十萬個唯一值，
雙向固定效應會產生天文數字的虛擬變數 → **kernel 直接崩潰**。

`obs_slot`（決策 12 的 10 分鐘對齊時間）四天僅 353 個層級。

### 降雨效果呈門檻型，線性設定會誤導

九天樣本（8/20–8/28）分級估計：

| 分級 | 係數 | p 值 | 樣本 |
|---|---|---|---|
| 0.5–1mm | 0.014 | 0.37 | 9,096 |
| 1–3mm | 0.096 | 0.28 | ~1,200 |
| >3mm | **0.185** | **0.049** | ~400 |

單調遞增，且成長超過雨量比例（light→mid 雨量差 5 倍、效果差 7 倍）。
線性設定給出 0.032，**同時低估強降雨、高估弱降雨**。

行為解讀：飄雨不改變決策；下到會淋濕的程度人就不騎；再大也不會更不騎。

### 處理變異稀缺是主要限制

九天 90 萬筆觀測，但僅 1.90% 有降雨，其中 75% 為 0.5mm，
3mm 以上僅約 400 筆（0.04%）。有效降雨日僅 5 天，皆為夏季午後短時對流。

拉長期間效果有限：四天→九天處理組增 50%，但標準誤反而變大
（新增的三個晴天貢獻 38 萬筆零處理變異的觀測）。

**限制不在觀測數，在降雨事件的數量。** cluster 處理了站點間相關，
但同一場雨的時間相關未處理 → 名義上 90 萬觀測，有效獨立處理事件僅數個。

### 樣本天然條件在「有活動的時刻」

決策 2 的副作用：無借還活動時不產生新列。
降雨最強的效果可能是「讓活動歸零」，而那些時刻不在樣本裡 → **估計為下界**。

補齊時間軸是可行的穩健性檢查，但會引入大量不提供識別資訊的零值
（尤其深夜），使標準誤虛假地縮小。

### 深夜為調度主導時段

日內模式顯示凌晨 3–5 點 `delta_per_min` 為全天最大正值。
分析樣本限制在 6:00–22:00。
