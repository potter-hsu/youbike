# Schema 設計

> 資料源：臺北市 YouBike 2.0 即時資料
> 最後更新：2026-08-06

---

## 一、表結構

### 1. `stations` — 站點慢變屬性

| 欄位 | 來源 | 說明 |
|---|---|---|
| `sno` | `sno` | 站點編號，PK |
| `name_zh` | `sna` | 站名（中文） |
| `name_en` | `snaen` | 站名（英文） |
| `area_zh` | `sarea` | 行政區（中文） |
| `area_en` | `sareaen` | 行政區（英文） |
| `address_zh` | `ar` | 地址（中文） |
| `address_en` | `aren` | 地址（英文） |
| `latitude` | `latitude` | 緯度 |
| `longitude` | `longitude` | 經度 |
| `quantity` | `Quantity` | 總車柱數 |
| `first_seen_at` | — | 首次觀測到此站的時間 |
| `last_seen_at` | — | 最近一次觀測到此站的時間 |

**SCD 策略：覆蓋更新（Type 1）**，不保留歷史版本。
理由：站名變更、站點遷移、車柱擴充皆為低頻事件，第 1 週不值得為此增加複雜度。
但 `first_seen_at` / `last_seen_at` 保留了「這站何時出現、何時消失」的粗粒度資訊，
未來若需升級為 Type 2（`valid_from` / `valid_to`），現有結構可平滑擴充。

### 2. `snapshots` — 時序觀測值

| 欄位 | 來源 | 說明 |
|---|---|---|
| `sno` | `sno` | 站點編號，PK 之一，FK → stations |
| `info_time` | `infoTime` | **該站回報數值的時刻**，PK 之一 |
| `available_rent_bikes` | `available_rent_bikes` | 可借車輛數 |
| `available_return_bikes` | `available_return_bikes` | 可還空位數 |
| `act` | `act` | 站點啟用狀態（'0' / '1'） |
| `first_fetched_at` | — | 首次抓到這筆資料的時間 |
| `last_fetched_at` | — | 最後一次抓到這筆資料的時間 |

**主鍵：`(sno, info_time)`**

### 3. `fetch_log` — 系統行為紀錄

記錄的不是 YouBike 資料，而是**抓取程序做了什麼**。

| 欄位 | 說明 |
|---|---|
| `fetch_id` | 流水號，PK |
| `started_at` | 抓取開始時間 |
| `duration_ms` | 耗時 |
| `status_code` | HTTP 狀態碼 |
| `etag` | 回應的 ETag |
| `update_time` | 整包資料的 `updateTime`（全站共用，不進 snapshots） |
| `stations_received` | 收到幾個站 |
| `rows_inserted` | 實際寫入幾列 |
| `rows_updated` | 更新了幾列（撞主鍵） |
| `error_message` | 失敗原因，成功則為 NULL |

> ⚠️ **待補：** 上表是初版，是否還需要其他欄位待第 2 週實作時確認。
> 判準：第 6 週要能只靠這張表回答「系統過去 24 小時正常嗎」。

## 二、關鍵決策與理由

### 決策 1：切三張表，而非單一寬表

站點靜態屬性（站名、地址、經緯度）若隨每次快照重複儲存，
以 1784 站 × 288 次/天計算，一天將重複寫入約 51 萬次相同文字。

`fetch_log` 獨立的理由不同——它記錄的是**系統狀態**而非**觀測資料**，
兩者的生命週期、查詢模式、保留策略都不同。

**沒有它就無法區分「抓了但資料沒變」與「程序掛掉沒抓」**，
第 6 週的監控會失效。

---

### 決策 2：主鍵用 `(sno, info_time)`，不用 `(sno, fetched_at)`

**背景：** 觀測到有站點失聯超過一年半（捷運東門站 3 號出口，`infoTime` = 2025-02-27），
API 仍每次照常回傳，外觀與正常站無異。

| 主鍵選擇 | 該站 288 次抓取後的列數 |
|---|---|
| `(sno, info_time)` | **1 列** |
| `(sno, fetched_at)` | 288 列 |

選前者的理由：

1. **天然冪等**——同一份資料重複抓取，寫入結果不變，直接滿足第 2 週需求
2. **不產生假紀錄**——失聯站不會生成 288 筆/天標著今日時間卻是舊值的資料，
   避免污染第 4 週的因果估計（該序列會是一條完全靜止的假時間序列）

代價是丟失「我在某時刻確實抓到這站」的資訊，
以 `last_fetched_at` 欄位補回：撞主鍵時更新此欄。

**附加價值：** `last_fetched_at - info_time` 即為該站的資料延遲，
不需另外計算，資料新鮮度監控可直接查詢。

實作對應 PostgreSQL 的 `INSERT ... ON CONFLICT DO UPDATE`（upsert）。

---

### 決策 3：`Quantity` 歸 `stations`（已驗證）

**驗證方法：** 取 8/4、8/5 兩個時間點的快照，
篩選 `act = '1'` 且 `gap ∈ [1,5]` 的站，以 `sno` merge 後比對。

**結果：** 317 站中，`Quantity` 變動筆數為 **0**。

**結論：** 單日內無變動，屬慢變欄位。

**但書：** 一日觀察不足以推論長期。車柱擴充是真實會發生的事件，
僅頻率低。建議累積 2 週資料後回頭複驗；
若確認長期穩定，此結論可視為定案。

---

### 決策 4：`act` 存進 `snapshots`，每筆重複

`act` 本身是慢變欄位（一年可能僅變動數次），照理應歸 `stations`。
但觀測到一個現象改變了判斷：

**`act = 0` 的站點，其 `infoTime` 呈現群聚：**

```
2026-07-10 06:57:04  溫州停車場、古亭站、動物園站、濟南紹興、螢橋公園
2026-07-10 06:58:02  潭美街、東湖國小、東湖一號公園、西湖國中、八仙里、薇閣
2026-07-10 06:59:02  復華花園、龍山寺、洛陽停車場
2026-07-10 07:28:04  榮星花園、林安泰、中山北路、南京新生
```

秒數完全相同、橫跨不同行政區、間隔約一分鐘
→ 這是**一次批次操作**，而非各站獨立故障。

**推論：** `act` 反映營運決策（施工、汰換、季節性停用），
若觀測期間內有站被停用，對該站的時間序列而言是**結構性斷點**，
不可當作雜訊濾除。

若 `act` 僅存最新值於 `stations`，將永遠無法得知某站何時被停用。
存入 `snapshots` 後，可用 window function（`LAG`）直接查出狀態轉換時點。

單一字元的重複儲存成本，遠低於遺失狀態變更歷史的代價。

---

### 決策 5：建兩個索引

| 索引 | 服務的查詢 |
|---|---|
| `(sno, info_time)`（主鍵自帶） | A：單站的時間序列（建模用） |
| `(info_time)` | B：某時刻的全市橫斷面（空間分析用） |

複合索引 `(sno, info_time)` 以 `sno` 為第一排序鍵，
查詢 B 僅提供 `info_time` 條件時無法利用，故需獨立索引。

每個索引都會增加寫入成本與儲存空間，兩個是合理起點，不預先過度建置。

---

### 決策 6：不儲存的欄位

| 欄位 | 原因 |
|---|---|
| `mday` | 與 `infoTime` 完全相同 |
| `srcUpdateTime` | 與 `updateTime` 完全相同 |
| `infoDate` | 可由 `info_time` 導出 |
| `updateTime` | **全站 1784 筆共用同值**，屬「整包資料」的屬性而非站點屬性 → 移至 `fetch_log` |

## 三、已知資料特性（影響後續建模）

### `gap` 是動態的，不可用 `Quantity` 當可用容量

定義 `gap = Quantity - available_rent_bikes - available_return_bikes`。

**觀測：**
- 全體站點中 `gap > 0` 者佔 35.6%（635/1784）
- 無負值（`rent + return ≤ Quantity` 恆成立）
- `gap` 分布呈幾何遞減：0→1147, 1→402, 2→136, 3→38, 4→12, 5→12
- 跨日比對（317 站）：差值分布對稱，0→186, ±1→96, ±2→23, ±3→9, ±4→3

**解讀：** 差值有增有減，代表佔用車柱的物件會流動，
而非「柱子陸續損壞」的單向累積。
最可能的解釋是充電中的電輔車——電量不足時不可借、佔用車柱，充飽後回到可借狀態。
（此為推論，可透過檢驗 `gap` 是否具日內週期性驗證，非當前優先事項。）

**對建模的影響：**
> 使用率不可計算為 `available_rent_bikes / Quantity`，
> 分母會系統性偏大。實際可用容量為 `rent + return`。

---

### 時間欄位：`TIMESTAMPTZ` + Python 端標記時區

原始資料的時間欄位皆為 `YYYY-MM-DD HH:MM:SS`，**不含時區標記**。
經與抓取時間比對，判定為 UTC+8。

**決定：欄位型別用 `TIMESTAMPTZ`，時區資訊在 Python 端補上後才寫入。**

**理由：** 若寫入不帶時區的字串到 `TIMESTAMPTZ`，PostgreSQL 會依「當下連線的
timezone 設定」補值。本機為 Asia/Taipei、EC2 預設為 UTC，同一份資料會差 8 小時，
且**不會報錯**——第 4 週跑模型時才會發現尖峰落在半夜。

在 Python 端明確標記後，資料庫收到的已是帶時區的值，
正確性不依賴部署環境的設定。

**替代方案（未採用）：** 用 `TIMESTAMP` 並全系統約定台北時間。
較簡單，但該約定只存在文件中、無機制強制，
且第 3 週接入氣象署資料後將有多種時間格式並存，靠約定難以維持。

---

### `sarea` 並非全為行政區

除「大安區」「中正區」等行政區外，另有「臺大公館校區」等非行政區值。
若進行行政區層級的彙總分析，此類值將成為孤兒類別。

**目前處理：** 原樣儲存，不做正規化。
若第 4 週需要行政區分析，再建立對應表處理。
